## 9.1 Eval tooling: run it where the data lives

By late 2026 every major model provider offers an evaluation feature in its platform (datasets, graders, runs,
comparisons), and there is a crowded field of open-source and commercial eval and observability tools that store
datasets, run graders, track scores per prompt version and draw the comparison charts. They are genuinely useful for
the bookkeeping: run history, side-by-side diffs, a place for reviewers to read failures. They also come and go: when
we read OpenAI's evals guide on 21 October 2026, it said its Evals platform is being deprecated, with a scheduled
shutdown on 30 November 2026, the very Monday of Godavari's week-6 run. An eval suite whose definitions lived only in
a hosted platform would have to move in the week it mattered most.

Three rules when you choose one for a customer like Godavari:

- **It runs where the golden set lives.** A hosted eval service that needs the real files uploaded is a data
  transfer the CISO has not approved (D08). Self-hosted, or the tool sees only the masked set and scores; the real
  run stays on the machine in the building.
- **The definitions stay in your code.** The normaliser, the four outcomes, the strata and the gate policy are the
  metric (Day 9 signed them). A tool's built-in "accuracy" or "correctness" grader is someone else's definition.
- **It does not replace the guide, the labellers or the adjudication log.** No tool knows that the PAN comes only
  from the PAN card.

The chapter's harness is standard-library Python on purpose: about 1,700 lines with its docstrings, readable in an afternoon, runnable
offline in the customer's environment, and portable into whatever tool the customer's team already uses.

## 9.2 Model-assisted labelling, carefully

Pre-labelling (the model fills in the form; the analyst corrects it) can halve labelling time, and in 2026 most
labelling tools offer it. The cost is **anchoring**: people accept a plausible pre-filled value more often than they
would have typed it themselves, and the system's own mistakes become the answer key. That is the model grading
itself through a human.

If you use it: never for the test split's first labels; or, if the time saving is essential, run a slice of 20 to
30 files both ways (blind and pre-labelled) and measure the difference before trusting the pre-labelled ones. The
eval owners must know which labels were pre-filled.

## 9.3 Synthetic data for evals

Generating varied test inputs with a model (unusual layouts, rare document combinations, adversarial notes) is a
good way to widen the **development** split and to write unit tests for the envelope. It is not a source of **truth**
for the test split. A model-generated file with a model-generated answer measures how well one model agrees with
another. This chapter's synthetic files are generated by deterministic code with a known answer, which is a
different thing, and even so section 02.6 is explicit about what they cannot teach.

## 9.4 Trajectory and agent evals

As workflows become multi-step (Day 17's state machine with tool calls), the eval grows from "is the answer right"
to "was the path acceptable": did the agent check the PAN card against the form before deciding, did it stay
within its tool budget, did it ask for approval before the write. The expert trajectories recorded in section 03.4
are the benchmark: compare the agent's steps with the analysts', report the steps it skipped, and gate on the ones
that matter (an agent that reaches PUSHED_TO_CORE without the approval step fails, however right its fields are).
The OpenAI semiconductor and coding examples evaluate against expert trajectories in exactly this way.

## 9.5 Online evals and shadow mode

The golden set is an offline eval. Online evaluation measures the same metrics on live traffic: a sampled stream of
production files re-labelled by analysts weekly, corrections in the review queue counted as labelled data, and, before
a new model or prompt is switched on, **shadow mode** (the candidate runs on every live file beside the current
system, its outputs are scored and never shown). Day 19 owns the dashboards and Day 27 owns running the golden set as
a production check after every deployment. The rule that connects them: the same definitions, the same normaliser
and the same strata, offline and online, or the two numbers cannot be compared.

## 9.6 Judges in 2026

Three judge patterns are common and worth knowing:

- **Pairwise judging** ("which of these two notes is better?") is easier for a model than absolute scoring and is
  how many model comparisons are run. It has a known **position bias** (the first answer is preferred), so run every
  pair twice with the order swapped, and count a win only when both orders agree (Zheng et al., 2023).
- **Reasoning models as judges** produce longer critiques and are often better at catching specific defects. They are
  slower and costlier per item, and they still need the calibration of section 06.6; a fluent critique is not a
  correct one.

## 9.7 What is hype

| Claim | What is true instead |
|---|---|
| "LLM judges have replaced human labels" | judges scale human judgement once calibrated against it; the labels still come from the customer's experts |
| "Our model scores 9x percent on benchmark X, so it will do well on your files" | no public benchmark contains a Guntur phone photo of a Telugu income declaration; only the golden set does |
| "We generated a thousand-example eval set with GPT" | a model's answers to a model's questions; useful for development variety, not for truth |
| "Confidence scores tell you when the model is wrong" | confidence must itself be checked against labels; the trimmed prompt raised confidence and lowered accuracy |
| "One eval score per release" | one score hides the stratum that failed; the gate checks 36 |
| "The eval is done; the pilot can start" | the set grows and the gate runs until handoff, and after it (Day 28) |
| "a prompt optimiser found the best prompt" | on the split it was given; optimise on development, confirm on test, review it like any release |
| "100 percent accuracy is the goal" | the goal is a measured accuracy with uncertain cases routed to people (Day 9; Day 34's role-play) |

## 9.8 Key takeaways

- Use eval tooling for bookkeeping, where the data lives, with your definitions in your code.
- Pre-labelling anchors people; measure the effect before trusting it, never on the test split's first labels.
- Model-generated examples widen development; they never define truth.
- Agent evals compare paths with the experts' trajectories; online evals use the same definitions as offline ones.
- Swap order in pairwise judging, calibrate reasoning judges like any other, and optimise prompts on development only.
