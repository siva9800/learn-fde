## 3.1 SOAP in plain words

SOAP is a way for one program to call another by sending an XML document over HTTP and getting an XML
document back. Every message is an **envelope** with an optional **header** (security, routing) and a
**body** (the request or the answer). The **WSDL** is an XML file that describes the service: which
operations exist, what each request and response looks like, and where to send them. It was the standard
for enterprise integration in the 2000s, which is why a 2009 Indian lending system speaks it, and why in
2026 an FDE still meets it in banks, insurers, hospitals and government systems. Nobody chooses SOAP for a
new system. You integrate with it because it is there and it is not going anywhere.

This is the whole of one call to Godavari's core, as the chapter's hand-built client sends it:

```xml
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:tns="http://core.godavarifinance.example/lending/2009">
  <soapenv:Header>
    <wsse:Security xmlns:wsse="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-secext-1.0.xsd">
      <wsse:UsernameToken>
        <wsse:Username>SVC_KAAGAZ_SBX</wsse:Username>
        <wsse:Password Type="...#PasswordText">********</wsse:Password>
      </wsse:UsernameToken>
    </wsse:Security>
  </soapenv:Header>
  <soapenv:Body>
    <tns:GetApplicationByFileNumberRequest>
      <tns:FILE_NO>GF-25001</tns:FILE_NO>
    </tns:GetApplicationByFileNumberRequest>
  </soapenv:Body>
</soapenv:Envelope>
```

And the answer, for a file the 02:00 job has registered but nobody has keyed yet:

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"><soap:Body>
  <tns:GetApplicationByFileNumberResponse xmlns:tns="http://core.godavarifinance.example/lending/2009">
    <tns:ApplicationSummary>
      <tns:FILE_NO>GF-25001</tns:FILE_NO><tns:BRANCH_CD>KKP01</tns:BRANCH_CD>
      <tns:APPL_STAT>S</tns:APPL_STAT><tns:CRT_TS>20261110110000</tns:CRT_TS>
    </tns:ApplicationSummary>
  </tns:GetApplicationByFileNumberResponse>
</soap:Body></soap:Envelope>
```

Both are copied from the cassette the contract tests replay (`code/contracts/cassettes/`), with the
password scrubbed. `APPL_STAT` `S` means "shell": the file exists, no application does.

## 3.2 Reading a WSDL in ten minutes

A WSDL 1.1 file has five parts. Read them in this order, not the order they appear:

| Part | What it tells you | What to write down |
|---|---|---|
| `service` / `port` | the address (`soap:address location`) | is it a real host? At Godavari it is a 2009 developer's machine, `corelend-dev01:7001` |
| `binding` | style (document or rpc), use (literal or encoded), the SOAPAction per operation | document/literal is the easy case; rpc/encoded is older and painful |
| `portType` | the operations, their input, output and fault messages | which of the 14 you actually need (four) |
| `message` | which schema element each input and output is | the wrapper element names |
| `types` | the XML Schema: every element, its type, `minOccurs`, order | the mandatory fields, the field order, any `xsd:import` |

Two things in Godavari's WSDL matter more than everything else in it:

1. **An `xsd:import` from a dead host.** The shared fault type lives in `common.xsd` at
   `http://corelend-dev01:7001/...`, a host that has not existed for years. A client that loads the WSDL
   from the server at start-up tries to fetch it and fails, or hangs: zeep's default timeout for loading
   documents is 300 seconds (zeep transport documentation, read 21 October 2026).
2. **`minOccurs` is not the whole truth.** The WSDL marks 23 of the 61 `CreateApplication` fields
   mandatory. Production enforces a 24th (`DLR_CD` for two-wheelers) in application code since the August
   release; the July sandbox does not. Section 10 turns that into a contract test.

The chapter's stand-in serves a WSDL with both defects (`standin/wsdl_gen.py`, served version). The
repository keeps a **vendored** copy with the import inlined and the address replaced by a placeholder,
and lists every difference at the top of the file. You never edit a vendored WSDL by hand without a note;
you regenerate it and review the diff with the owner.

A naming note: early drafts of the Part plan called the create operation `CreateLoanApplication`. The
WSDL the FDE read in week 1 (Day 6) calls it `CreateApplication`, and the WSDL wins; the plan and Day 12
now use the WSDL's name. On a real engagement the customer's contract is always the source of truth.

## 3.3 Generating a client with zeep

zeep reads a WSDL and gives you Python methods for each operation. The chapter pins zeep 4.3.3 (June
2026). The production decisions are all in the constructor:

```python
class OfflineTransport(Transport):
    """Loads schemas only from files or this machine."""
    def load(self, url: str) -> bytes:
        parsed = urlparse(url)
        if parsed.scheme in ("http", "https") and parsed.hostname not in LOCAL_HOSTS:
            raise WsdlFetchRefused(f"refusing to fetch {url} at run time; vendor it")
        return super().load(url)

transport = OfflineTransport(timeout=5, operation_timeout=timeout)     # load timeout, call timeout
client = Client(str(VENDORED_PATH), transport=transport,
                wsse=UsernameToken(username, password), settings=Settings(strict=True))
service = client.create_service(BINDING, url)                         # never the WSDL's address
```

- **The WSDL comes from the repository**, never from the server at run time. `OfflineTransport` makes the
  dead-host import fail in a test (`test_served_wsdl_with_dead_import_is_refused_at_load`) instead of at
  02:00.
- **Two timeouts, not one.** zeep's `timeout` is for loading WSDL and XSD documents; `operation_timeout`
  is for the calls. Setting only the first, which is what the zeep documentation's first example shows,
  leaves calls with no timeout at all.
- **The address is explicit.** `create_service(binding, url)` ignores the WSDL's `soap:address`.
- **`strict=True`.** zeep then rejects a response whose elements are out of the schema's sequence order.
  This caught a real bug while the chapter was being built: the stand-in returned `GetApplication`'s
  fields in dictionary order, and zeep refused to parse the reply. A lenient parser would have read it and
  hidden the drift. The test `test_strict_zeep_catches_sequence_drift_that_the_lenient_parser_accepts`
  keeps the lesson.
- **zeep checks `minOccurs` before sending.** A `CreateApplication` with no `MOB_NO` never leaves the
  machine; zeep raises a `ValidationError`, which the port turns into `RefusedBeforeSending`. The
  hand-built client sends it and the core answers `CL-E023`. Same outcome, different place; the contract
  test records the difference on purpose.

## 3.4 Faults, and the things that look like faults

A SOAP 1.1 fault is an HTTP 500 whose body holds `soap:Fault` with a `faultcode` (`soap:Client` means you
sent something wrong, `soap:Server` means the server could not do it) and a `faultstring`. Godavari's core
puts its own code at the start of the string and, usually, in a `detail` element:

```xml
<soap:Fault><faultcode>soap:Client</faultcode>
  <faultstring>CL-E023 MANDATORY FIELD MISSING: MOB_NO</faultstring>
  <detail><tns:CoreError><tns:Code>CL-E023</tns:Code><tns:Field>MOB_NO</tns:Field></tns:CoreError></detail>
</soap:Fault>
```

The fault catalogue (`corespec.FAULTS`) says which codes are worth retrying, and when:

| Code | Means | Retry? |
|---|---|---|
| CL-E017 | batch in progress, writes not permitted | later, after the batch; it is a deferral, not a failure |
| CL-E099 | service busy (the undocumented rate limit) | yes, after backing off |
| CL-E023, CL-E031, CL-E040, CL-E041 | mandatory missing, invalid code, too long, bad format | never; fix the data or the mapping |
| CL-E052 | file not registered (no shell) | never; the 02:00 job did not see this file |
| CL-E001 | authentication failed | never automatically; page a person |

Two replies look like faults and are not:

- **The maintenance page.** On Sunday mornings (06:00 to 09:00 in the stand-in, a window agreed in the
  integration contract) the load balancer in front of the core answers HTTP 503 with an HTML page. The
  core never saw the request. zeep reports this as `Fault("Unknown fault occured")` with the HTML bytes
  in `detail`; a client that treats every `Fault` as a business rejection marks the file failed. The
  port maps it to `CoreUnavailable`: safe to retry later.
- **A reply it cannot parse.** For a read that is a broken contract; for a write it is ambiguous, because
  the core probably did the work. The port raises `ResponseUnreadable`, a kind of `AmbiguousOutcome`.

Read the code from `detail` first, from the text second, and never from the HTTP status alone.

## 3.5 The four outcomes

Every call the integration makes ends in exactly one of four ways, and the only question that matters for
a write is "did it happen?":

| Outcome | Raised when | Did the core do the work? | What the writer may do |
|---|---|---|---|
| `CoreFault` | the core answered with a fault | no | retry the retryable codes later; otherwise stop |
| `CoreUnavailable` | something in front answered (503 page, proxy error) | no | retry later |
| `NotSent` | connect refused, DNS failure, connect timeout | no | retry |
| `AmbiguousOutcome` | read timeout, connection dropped after sending, unreadable reply | maybe | **never retry a write**; resolve by lookup after a quiet period (section 04) |

The split between `NotSent` and `AmbiguousOutcome` is the timeout split. `requests` takes a tuple
`timeout=(connect, read)`: a connect timeout means nothing was sent; a read timeout means it was sent and
nobody knows what happened. `soap/base.py` holds the classification, and both clients share it.

## 3.6 When the WSDL is broken: the hand-built envelope

Sometimes the WSDL will not load at all: an import that cannot be fixed, an rpc/encoded binding the
library mishandles, a vendor extension. Then you build envelopes by hand. `soap/raw_client.py` does it in
about 150 lines with `requests` and the standard library's XML parser:

```python
def build_request(operation: str, payload: dict, username: str, password: str) -> bytes:
    if operation == "CreateApplication":
        unknown = sorted(set(payload) - set(FIELD_BY_NAME))
        if unknown:
            raise ValueError(f"not in the data dictionary (the core would drop them silently): {unknown}")
        inner = "<tns:Application>" + "".join(_el(n, payload[n]) for n in _ORDER
                                              if payload.get(n) not in (None, "")) + "</tns:Application>"
    ...
```

Two rules make a hand-built client safe. **Element order follows the schema**, so it is built from the data
dictionary's field order, not from a dictionary's. **Element names are checked before sending**, because
the 2009 core silently ignores an element it does not know: `test_the_core_silently_drops_an_element_it_does_not_know`
sends `EMPL_NM` instead of `EMP_NM`, gets HTTP 200 and an application ID back, and the employer is gone.

| | zeep (generated) | hand-built envelope |
|---|---|---|
| code to write | small | about 150 lines |
| catches schema mistakes | before sending (`minOccurs`, types, order with `strict`) | only what you check yourself |
| when the WSDL is broken | vendor and fix it, or cannot be used | works |
| what is on the wire | hidden unless you add a plugin | in front of you, easy to record |
| failure modes | library quirks ("Unknown fault occured" for HTML) | typos, order, escaping |

Godavari's integration uses zeep for the writer and the hand-built client for recording the sandbox and
for the reconciliation job, and the contract tests require both to read every recorded exchange the same
way. Two independent clients that agree are evidence; one client agreeing with itself is not.
