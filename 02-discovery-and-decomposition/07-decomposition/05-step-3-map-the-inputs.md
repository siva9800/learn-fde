## 5.1 Data as it actually is

Every sponsor describes their data the way the system diagram describes it: "the loan files are in the
core system", "we have all the documents", "the data is in the warehouse". [Day 6](../06-discovery-interviews/README.md)
taught you to sit beside the operators and find the data as it actually is: scanned PDFs on an SFTP
server, an Excel tracker that is the real state, WhatsApp photos that never reach the file of record.
Step 3 writes that reality down as a table with five columns that engineers forget and sponsors never
mention: **shape, owner, freshness, access, and what is missing.**

The guides are blunt about why this step is scored: interviewers want to see you reason "about data as
it actually is, including likely join failures", and the discovery playbooks tell you to "inspect the
data path: which systems generate inputs, which schemas conflict, where fields are incomplete". A
candidate who says "we would index the documents" has assumed the documents exist in a form that can be
indexed. A candidate who asks "are the documents labelled by type and page, or is a file one 40-page
scan with no index?" has found a workstream.

## 5.2 The five columns, and the question behind each

| Column | The question | Why it changes the architecture |
|---|---|---|
| **Shape** | What does one unit look like? A row, a PDF, an XML message, a photo, a spreadsheet? How big, in what language, how consistent? | a 40-page mixed-language scan with no page index needs classification before extraction; a REST JSON feed does not |
| **Owner** | Who can say yes to reading it, and who can say yes to writing it? A person, not a department. | the owner's goodwill is a dependency; the core-system owner has watched three vendors fail |
| **Freshness** | How stale is it when you read it? Real time, nightly batch, quarterly refresh, "whenever someone updates the sheet"? | a nightly SFTP batch means the tool cannot promise same-hour intake; a quarterly sandbox refresh means integration tests go stale |
| **Access** | How do you reach it today, and what is needed to reach it in production? A ticket, a service account, a security review, a physical visit? | access tickets are on the critical path; a review that takes eight weeks has to start in week two |
| **What is missing** | What is not there, not trustworthy, or not labelled? Which field is free text? Which join will fail? | missing ground truth means the eval set is a workstream with customer experts; free-text send-back reasons mean no categories to learn from |

Add a sixth column for your own use: **the architecture risk**, the single sentence that says what
this input forces the design to do. It is the sentence you will say out loud in the interview.

## 5.3 Godavari's inputs

Built from Day 6's shadowing and generated by the chapter's code (section 12 runs it; everything is
synthetic):

| Input | Shape | Owner | Freshness | Access today | What is missing | Architecture risk |
|---|---|---|---|---|---|---|
| Loan application PDFs | scanned, 8 to 40 pages, English and Telugu, some phone photos | branch ops produce, credit-ops read | nightly SFTP batch; up to 24 h before an analyst sees it | SFTP on-prem; read-only service account via an IT ticket | no page index; 31 percent lack a mandatory document | page classification is a workstream, not a detail |
| Core lending system SOAP API (2009) | WSDL, 14 operations; CreateApplication has 61 fields, 23 mandatory | the core-system owner | writes visible after the nightly batch | sandbox refreshed quarterly; production write needs the CISO and the owner | no idempotency: a retry creates a duplicate | the integration layer must own idempotency before any automation |
| Excel file tracker | 40 workbooks, 19 columns, free-text status, colour coding carries meaning | credit-ops team lead | minutes; it is the true state of every file | shared drive; no API | no timestamps on status changes | the tool must read and write the real state or it will be ignored |
| Active Directory groups | a group per branch and per role, synced nightly from HR | corporate IT | nightly; transfers lag a day | LDAP for service accounts after a review; no vendor SSO today | no "all branches" group; the ops lead is a manual exception | every query filters by the caller's groups (Days 15 and 22) |
| WhatsApp photos | JPEG pages to analysts' personal numbers | nobody | same day | not allowed as an input | the pages never reach the file of record | the tool must make resubmission through the proper channel easy |
| RBI KYC rules and the internal checklist | the Master Direction plus a Word checklist per product | the compliance head | changes by RBI notification; the checklist lags | public, plus the compliance drive | acceptable alternatives (which address proofs) not listed | completeness rules are deterministic code the compliance head signs (Day 11) |
| Historical decisions | 28,000 files; statuses in the core system; send-back reasons as free text | credit-ops and the core-system owner | historical | a report on request | no field-level ground truth | the golden set must be labelled by experts (Day 14) |

Seven rows, and every row changed something. Without this table the design is "extract fields from
PDFs and write them to the core system". With it, the design has a classification step, an idempotency
key, a tracker integration, group-filtered access, a resubmission flow, signed deterministic rules, and
an expert-labelled eval set. Not one of those came from thinking about models.

## 5.4 Data that does not exist

The most valuable line in step 3 is the one under the table: **data that does not exist yet, and who
will create it.** Two kinds appear on almost every engagement:

- **Ground truth.** Nobody at Godavari has ever recorded, per file, what the correct value of each
  field was. The core system has what the analyst typed, which includes the analyst's errors. To know
  whether extraction works you need 100 to 200 files labelled by senior analysts, and that is a
  workstream with people in it, not a download. Day 14 builds it; step 3 is where you say it must exist.
- **The baseline.** The tracker has no timestamps, so "9.2 days" cannot be pulled from a query. It has
  to be sampled by hand for two weeks (Day 9). If you do not plan the sample, you will never prove you
  helped.

Interviewers listen for this. "What data do you wish you had, and how would you get it?" is a question
they ask when the candidate does not volunteer it. Volunteer it.

## 5.5 The inputs you must plan around but cannot use

The WhatsApp row is there on purpose. One in five files has a page that arrived by a channel the
compliance head will not allow. You cannot ingest it. You still have to plan for it, because those
pages will show up as "missing" in every completeness check and the analysts will blame the tool. The
plan is a resubmission flow: the tool tells the branch, on day one, exactly which page is missing and
how to send it properly. An input you cannot use is still an input.

## 5.6 The synthetic sample, read as step 3

Section 12's generator also writes a two-week sample of 200 loan files so that the chapter has something
to count. Read as a step-3 artefact:

```text
files by channel:        mixed 54, phone_photo 31, sftp_scan 115
sent back at least once: 63 of 200 (32%)
median turnaround:       9.2 days
mean analyst hours/file: 4.6 h

what is missing, by document (share of files without it):
  has_pan                10%
  has_address_proof      18%
  has_income_proof       14%
  has_photo               4%

send-back rate by channel:
  mixed          44%  (n=54)
  phone_photo    55%  (n=31)
  sftp_scan      19%  (n=115)
```

Three things an FDE reads off this in a minute. Address proof is the most common gap, so the
completeness rules for address proof (and the acceptable alternatives the checklist does not list) are
worth the compliance head's time first. Files that arrived partly by phone photo are sent back two to
three times as often as clean SFTP scans, which is why the walking skeleton starts with SFTP scans only.
And the sample reproduces the engagement's known numbers (about 31 percent send-backs, about 9 days,
about 4.5 hours), which is what a synthetic sample is for.

## 5.7 What step 3 sounds like in the interview

> "What data exists, and in what shape? I would expect the loan files to be scanned PDFs rather than
> structured records; if so, are the pages labelled by document type, or is a file one long scan? I
> would assume unlabelled, which makes classification its own piece of work. Where do they arrive and
> how fresh: a nightly batch, I would guess. The core system we write to: what is its interface and does
> it tolerate retries? A 2009 system with a SOAP API probably does not, so idempotency is on us. Is there
> an unofficial tracker the analysts actually use? There almost always is. Who may see which files, and
> where does that rule live today? And the data that does not exist: has anyone ever recorded the correct
> value of each field, per file? If not, the first thing we build with the customer is a labelled set,
> because without it nobody can say whether extraction works."

Every sentence is a question or a flagged assumption. The architecture is accumulating, but you have
not said what it is.

## 5.8 Key takeaways

- Five columns per input: shape, owner, freshness, access, what is missing. Add the architecture risk.
- Every row should change something in the design. If a row changes nothing, you have not asked enough.
- Write the data that does not exist yet (ground truth, the baseline) and who creates it.
- Inputs you cannot use still have to be planned around.
